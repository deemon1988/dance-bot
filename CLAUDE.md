
## Цель проекта

Разработка Telegram-бота на Python с использованием:
- **aiogram** — Telegram Bot API
- **python-dotenv** — управление переменными окружения
- **pytest** — тестирование

Другие библиотеки — только при необходимости и с разрешения пользователя.
Код должен быть пригоден для production-использования и дальнейшего расширения.

## Команды разработки

```bash
# Активация виртуального окружения
source .venv/bin/activate

# Установка зависимостей
pip install -r requirements.txt

# Запуск бота
python -m bot          # из директории src/
# или
python src/bot/main.py

# Запуск всех тестов
pytest tests/

# Запуск одного теста
pytest tests/test_text_service.py -v

# Линтинг (если настроен)
ruff check src/ tests/
```

## Структура проекта

```
.
├── README.md
├── requirements.txt
├── .env / .env.example
├── src/
│   └── bot/
│       ├── __main__.py        # точка входа: python -m bot

│       ├── services/          # бизнес-логика (не зависит от aiogram)

└── tests/                     # unit-тесты сервисного слоя (pytest)
```

Отклонения от структуры — только по согласованию с пользователем.

## Архитектурные правила

- `main.py` — единственная точка инициализации и запуска бота (polling)
- `routers/` — только обработчики Telegram, без бизнес-логики
- `services/` — бизнес-логика, изолированная от aiogram и Telegram
- Один файл — одна ответственность, до 300 строк (исключения: автогенерация, декларативные структуры)

## Базовые инженерные принципы

- **Архитектура по контексту:** production — SOLID и Clean Architecture; скрипты/прототипы — прагматичный подход
- **Слабая связанность:** внешние зависимости передавать через DI и абстракции
- **Атомарные изменения:** каждое изменение небольшое, локальное и легко откатываемое
- **Без дублирования:** перед добавлением кода проверить кодовую базу на существующие решения
- **Явное лучше неявного:** запрещена скрытая логика и неочевидное поведение

## Качество и стиль кода

- Явная типизация на границах системы: публичные функции, сервисный слой, интеграции, модели данных
- `Any`, `type: ignore`, `# noqa` запрещены по умолчанию (допускаются точечно, с пояснением причины)
- Магические значения запрещены — константы выносить на уровень модуля в `UPPER_CASE`
- Имена переменных, функций и классов должны быть самодокументируемыми
- Неиспользуемый и устаревший код удалять
- Конкретные типы исключений с понятными сценариями отказа
- Запрещено добавлять токены, ключи, секреты и персональные данные в код, логи или промпты

## Зависимости и окружение

- Все зависимости фиксируются в `requirements.txt` — любое изменение требует обновления файла
- Изменения зависимостей — только с разрешения пользователя
- Нельзя полагаться на глобально установленные пакеты
- Все установки и запуски — только в виртуальном окружении проекта (`.venv/`)
- При предложении новой библиотеки — указать цель и область использования

## Проверка документации через MCP Context7

При работе с библиотеками, фреймворками или API **обязательно проверять актуальную документацию** через MCP-сервер Context7:

1. Сначала вызвать `resolve-library-id` для получения ID библиотеки
2. Затем вызвать `query-docs` с конкретным вопросом

Это касается любых случаев, когда:
- Используется API библиотеки (aiogram, pytest, python-dotenv и др.)
- Нужно проверить сигнатуру функции, параметры или поведение
- Есть сомнения в правильности использования метода или класса
- Добавляется новая зависимость или обновляется существующая

**Запрещено угадывать API или поведение библиотеки** — если информации недостаточно, проверить через Context7 или задать вопрос пользователю.
